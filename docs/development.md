# 插件开发约定

## 独立边界

每个插件在根目录使用有业务含义的 `kebab-case` 文件夹，目录内维护自己的源码、manifest、说明、依赖锁文件、测试和版本记录。插件 ID 必须唯一，发布后保持稳定；目录名、显示名称和 ID 的对应关系记录在插件 README。

插件能单独检查、构建、打包和安装，不直接引用相邻插件的源码、私有数据或开发机绝对路径。确需协作时先约定公开接口、兼容版本和依赖缺失时的行为。共享经验可以立即沉淀；公共代码仅在出现真实复用需求后提取，并确保进入各插件的独立安装包。

根目录 README 维护插件索引，各插件 README 维护详细状态，避免重复记录实时进度。复杂插件按需增加需求、设计和任务文档，简单插件不创建空文档套件。

## SDK 与运行形态

从目标 cookieOS 实例获取扩展 SDK，记录宿主版本、SDK 来源及文件摘要。选择满足功能的最小形态：`web` 仅界面，`node` 提供 JavaScript 服务，`native` 提供原生服务。以该版本 SDK 的说明、模板和宿主校验为依据，不默认跟随最新版本。

以下命令在工作区根目录执行。`COOKIEOS_SDK_DIR` 指向已获取的 SDK 目录；`my-plugin` 是创建实际插件时替换的示例名称，本仓库不预建该插件。

```sh
python3 "$COOKIEOS_SDK_DIR/dev.py" init ./my-plugin --runtime node
python3 "$COOKIEOS_SDK_DIR/dev.py" check ./my-plugin
mkdir -p dist
python3 "$COOKIEOS_SDK_DIR/dev.py" pack ./my-plugin ./dist/my-plugin-0.1.0.zip
```

原生插件在检查和打包前执行 SDK 的 `build` 命令。新增运行依赖必须进入可安装产物；不得依赖安装时执行 npm/pip 钩子。具体构建命令、平台和架构由插件自己的 README 明确。

界面通过 `window.xhub` 接入，不直接导入宿主内部前端文件；资源使用相对路径。按实际需要声明展示形态及能力，不要求每个插件都提供全部界面、AI 和 MCP 入口。

有后台工具的插件沿用 SDK 的服务启动、健康检查和令牌校验协议。manifest 声明参数和结果 Schema，服务仍须校验输入；HTTP 成功状态不能代替业务成功结果。UI、内置 AI 与 MCP 按需复用同一业务实现。

## 配置与数据

普通配置使用宿主配置入口，秘密使用宿主秘密配置入口，不放入 manifest、安装包、公开配置或日志。业务数据使用宿主提供的插件数据目录，临时文件和后台任务不得干扰其他插件。

当前 SDK 的可信模式不是恶意代码沙箱；插件可能访问运行账号可访问的文件和网络。每个插件应说明真实权限与外部影响。

升级、回退、停用、卸载分别说明配置、数据和后台任务的处理。SDK 的独立版本数据目录不等于业务数据自动迁移，外部系统已经发生的修改也不会随代码回退撤销。写工具遇到网络中断或结果未知时先查询结果，非幂等操作不得自动重放。

## 验证

有界面或重型能力的插件在规划阶段就明确首次可操作、工具切换、按需依赖、偏好读取与失败恢复、资源归属及可重复性能基线；按项目真实条件冻结预算，再接入现有检查。模块任务必须实际落盘；具体检查清单与Ctool案例见[加载性能规划经验](experience.md#规划时就纳入加载性能与稳定性2026-10-31)，不照搬Ctool的数字或复杂度。

每个插件保留最小相关检查，并记录命令、结果、宿主版本、平台和未验证项。非平凡业务逻辑应有可运行的行为测试。

发布前按实际能力验证：本地检查与构建、隔离测试实例安装、核心业务与失败路径、声明的 UI/AI/MCP 入口、配置变更、升级回退、停用卸载，以及必要的多插件共存行为。使用独立测试数据，不能操作真实业务来制造测试证据。

SDK 的 `check` 只做本地预检。打包通过、模拟调用和离线验签分别记录，不冒充真实宿主、真实模型、MCP 客户端或业务验收。

## 独立发布

插件使用自己的语义版本，Git 标签采用 `<plugin-name>-v<version>`。对应 Release 的安装包只包含该插件，不能把整个仓库源码 ZIP 当作插件安装包。

顺序为：相关验证通过 → 生成安装包 → 创建对应 Release 并上传产物 → 下载核对 SHA-256 → 更新并签名市场清单。安装包发布后保持内容不变，修复使用新版本。只将已完成相关验证的版本加入市场。

本次初始化未固定任何插件的宿主兼容版本或平台；首次发布前必须记录真实验收结果。
