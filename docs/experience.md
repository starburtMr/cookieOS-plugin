# 共享开发经验

通用接入规则见 [开发约定](development.md)，市场规则见 [市场维护](market.md)。本页只沉淀经过验证、能被后续插件复用的结论，不重复复制协议文档。

## 规划时就纳入加载性能与稳定性（2026-10-31）

**后续插件在规划方案时就要明确首次打开、工具切换、按需加载、偏好安全和失败恢复，不等功能齐全后才第一次检查。** 这是本仓库后续插件的规划要求；具体性能数字按新插件的真实基线制定，不照搬Ctool的包体积或毫秒预算。DEV-PLAN只维护阶段和依赖，具体范围、修改文件、命令和验收落在插件自己的doc/tasks/；交付前实际检查文件存在、非空及链接有效。

依据：Ctool0.3.0[本轮源码/静态产物核对](../ctool/doc/research/loading-performance.md)与[七个执行模块](../ctool/doc/tasks/loading-performance/README.md)。本节的原始问题来自规划基线；0.3.1已实现并测量，实际收益、未达目标和限制见[加载优化验证](../ctool/doc/verification/loading-performance/README.md)，不能把旧静态数字当作当前传输量。

### 本次已确认、后续可复用的教训

- **异步组件不代表轻量入口。** Ctool的Editor已经异步注册，但全局序列化组件通过语言名称辅助模块加载完整Monaco。检查真实静态导入闭包和浏览器请求，不只看路由是否使用import()。
- **子路径和chunk名字不代表隔离。** 某些共享领域模块通过ToolError反引总入口；Lodash/crypto chunk又静态引用mathjs/Monaco chunk。将中立错误/校验/基础函数与工具注册分开，旧入口重新导出同一实现；不能删除校验、复制算法或一律标sideEffects=false。
- **并行读仍会阻塞挂载。** 0.3.0基线中11项偏好已Promise.all，但入口等待全部完成，再查询剪贴板、再加载初始路由。规划时画出“必要设置”和“当前工具资源”两条并行路径，权限仅在实际需要时初始化。
- **提早挂载必须同时设计偏好保护。** 设置不存在、读失败和非法值分开；水合不写默认值，迟到读取不覆盖用户修改，按键保存避免旧整份快照覆盖无关设置。SDK缺批量/CAS/通知时如实写边界，不凭空承诺。
- **await必须对应真正可用。** Editor.create内部没有等待实际初始化，外层await不能证明可编辑。就绪以实际输入、执行、正确结果判定；初始化中卸载、失败重试、监听/模型/Worker释放一起设计。
- **缓存测量与故障夹具分开。** Playwright route会禁用HTTP缓存；拦截转发验证成功不等于暖缓存速度已验。生产构建、真实缓存条件、请求传输/解压大小/长任务分别记录，固定样例多次比较。
- **重试不是重放业务。** 模块下载失败、模块求值失败、编辑器初始化失败、业务执行失败分别处理。动态import可能缓存求值失败，不能保证重置Promise就恢复；保留输入、有限重试，必要时明确重新打开。已发AI/收费/写操作不自动再发。
- **共享与自有资源分开。** 编辑器运行时可复用；组件自建model、监听器、计时器和任务Worker应释放。不能关闭一个编辑器就终止另一个仍需的语言Worker，也不能以缓存为由常驻全部页面。
- **准备发布时验证最终ZIP。** 产物递增版本、保留旧包和摘要；最终包隔离安装、打开形态、配置恢复、升级回退与失败路径分别验收。规划/构建成功均不表示这些已通过。

### 下个插件在规划阶段必须回答

1. 默认打开什么、如何处理上次入口；哪些能力必须首屏具备，哪些随当前页面加载？
2. 首屏静态闭包和Worker/CSS/字体会包含什么；基础元数据是否意外导入编辑器、工具注册或后端模块？
3. 必要设置何时应用；读取失败/迟到、多窗口修改、保存失败如何保持用户输入和原配置？
4. 谁拥有加载状态、输入草稿、取消信号、编辑器/Worker及监听器；关闭是销毁还是隐藏，SDK有哪些真实通知？
5. 从打开到正确结果怎么测，cold/warm/首次重工具/切换重开各测几次；按什么基线冻结预算并接入现有检查？
6. 加载失败能否局部重试；永久错误如何保护草稿；哪些外部副作用绝不能自动重试？
7. 哪些依赖/算法/校验器直接复用，哪些宿主限制单独列出；模块任务文件是否实际生成？

精简插件可在一个模块文件回答，不机械创建七份任务；复杂插件按依赖拆分。未验证的目标写“待验证”，真实证据写版本、条件和限制。失效条件：SDK、宿主缓存/生命周期、构建器、共享依赖或初始化时序变化时复核本节，不能沿用旧数字或把建议变成已验证收益。

## 加载优化实施经验（0.3.1）

依据：[本轮源码、样本和验证](../ctool/doc/verification/loading-performance/README.md)。后续插件在规划阶段就把这些约束放入自己的模块任务，具体数字重新建立基线。

- 显示元数据不要导入完整运行时。Ctool分别抽出91项编辑器语言数据、28种代码生成语言/302项选项；与真实版本逐项对照后再采用。完整编辑器和生成器仍随包交付，不能删语言或算法换体积。
- 要追到第二层导入。替换总入口后，radix和YAML仍可能反向引入注册表；旧错误类型必须re-export同一类，不能复制同名类破坏instanceof。分chunk不等于退出首屏，用modules/imports和真实请求一起证明。
- 偏好初始化不写默认值。区分未设置、失败和非法值；读取代次与本地修改代次隔离晚到响应，水合先建立保存对照再更新真实store。不同键逐键保存，避免整份设置互相覆盖；没有CAS时如实保留同键最后写入语义。
- SDK调用数和网络数分开。插件仍调用11次storage.get，本轮宿主桥实际合并为一次HTTP读取；这是该宿主已有行为，不能承诺未来SDK都批量化。权限按操作需要初始化。
- 默认选择明确后只预载当前工具；等待常用列表与语言就绪，避免提前求值把错误语言固定进选项。禁止后台遍历所有工具假装切换快。
- 失败重试只恢复资源，输入放在父层。新导航清除旧重试目标，取消导航也结束pending；不能因为重试编辑器、生成器或恢复网络而重放AI、JDoodle或写操作。
- 编辑器要等待真实Promise并清理自有模型；任务Worker真的terminate且保持原截止。十轮模型计数和快速切换通过只证明所测范围，不等于24小时无泄漏或所有Worker均被穷举。
- 性能测量终点必须产生正确结果。JSON/代码测试实际点击格式化并验证文本变化，不能只看到编辑器内已有输入就停止计时。带route拦截的故障测试不采HTTP缓存；固定宿主二进制、前端及最终ZIP摘要，避免并行构建使前后环境漂移。
- 首次打开、首次重工具与重复切换分别报告。完整Monaco按需加载会有首次成本；首屏JS大幅减少不保证整条宿主打开流程同比例加快。保留预算失败结果和所有样本，不抬阈值、不挑最快一次、不用小样本包装稳定P95。
- 公布的包只冻结一次。功能/结构验证、隔离安装、源码与原生清单复核后，使用最终ZIP生成市场条目和媒体；先公开资产再更新sequence与签名。相同原生库存可引用原版本不可变源码附件，避免每次重复上传大归档。

## Ctool 本地迁移（2026-10-30）

适用：SDK 1.1.0、Vue 3、Pinia 持久化插件 4.x、Node >=22。依据：[Ctool 进度与验证](../ctool/Progress.md)、[实际设计](../ctool/High-Level-Design.md)、[检查入口](../ctool/package.json)。

| 现象与原因 | 已验证处理 | 复核条件 |
|---|---|---|
| 原页面弹层失效：ES module 入口没有原 HTML 中的 Teleport 目标 | 挂载前补齐自己的弹层节点；逐项打开真实对话框验证，路由冒烟不能代替弹层交互 | 页面壳、入口或弹层组件变化 |
| 同步 Pinia storage 无法直接返回 xhub Promise；读失败后可能误写默认值 | 0.3.0先读允许偏好再挂载，保留同步内存镜像、逐键写队列和失败反馈；不自动覆盖远端。后续并行启动须按本页加载规划保护迟到读取与本地修改，不能直接去掉await | 初始化时序、持久化插件/桥语义变化；增加敏感历史前重新核定隔离 |
| SDK pack 递归收集目录，宿主不执行 npm 安装钩子 | 只组装干净目录，Node 依赖随 bundle 提供；在没有开发 node_modules 的临时目录启动服务，再检查和打包 | SDK pack 排除规则、运行时或依赖变更 |
| 单次 Worker 模块记录会遗漏其他 Worker 的依赖与许可 | 合并全部 Worker 和主界面的构建输入，按实际版本核对审计及许可；不把全工作区告警与实际包混同 | Worker 拆分、构建器或依赖变更 |
| 只有空文本框的页面被 toBeEmpty 误判为未挂载 | 检查实际控件节点和可见操作，再分别断言业务结果；保留失败证据并区分测试错误与产品缺陷 | 测试定位或渲染结构变化 |

更多 Ctool 业务差异留在插件目录。上述结论仅覆盖已记录的本地检查，不声明真实宿主 CSP、外部服务或全部浏览器兼容性。

## 下一个插件的开工顺序

适用：本仓库多插件开发，接入合同以该插件实际获取的 SDK 为准。以下顺序来自首个插件的开发和发布过程；新增插件的宿主适配仍须单独验收。

1. **确定落点。** 每个插件直接放在根目录的独立文件夹，例如 `./my-plugin/`，不要放进 `ctool/`。复用的是 SDK、经验和已有成熟库；不让新插件依赖 Ctool 的内部源码或开发机目录。插件 ID、目录、显示名称、版本分别明确，不能保留模板身份。
2. **先检查 SDK。** 先检查本地开发包的版本和内容；需要下载时保留 HTTPS 证书校验、超时和 HTTP 状态检查，确认是可读 ZIP。只解压到新目录，拒绝路径穿越和链接。阅读 README、技能、manifest/metadata schema、类型声明、所选模板和 `dev.py --help`，不要凭旧经验猜新 API；SDK 目录不能进入插件 ZIP。
3. **选择运行形态。** 仅界面选 web；确需服务优先 node；明确需要原生能力时再评估 native。已核实的 SDK 1.1/1.2 界面可调用宿主模型，但这不代表纯 web 插件自动拥有后台 AI/MCP 工具。宿主模型接口、后端工具协议和外部 MCP 是不同接入路径。
4. **先查复用再实现。** 先看项目组件、当前依赖和平台能力，缺口再查适用库的官方依据。复用已有格式解析、密码学、代码执行引擎等能力；新增依赖核对版本、运行位置、打包方式和许可证，不只确认能安装。
5. **把任务真正落盘。** 完整功能先记录范围和验收；DEV-PLAN 只放阶段、顺序及依赖，具体模块任务放插件自己的 `doc/tasks/`。任务中写修改范围、依赖、接口来源和验证方法；交付前检查文件存在、非空、链接有效。明确的小改动沿用已有记录，不重复搭一套计划。
6. **先贯通一条路径。** 从插件入口到实际结果接通后再扩展；UI、AI 和 MCP 对同一操作复用业务实现。只声明真实使用的能力、权限及工具，不把所有页面功能自动登记成 AI 工具。
7. **尽早验证最终形态。** 一条路径可用后就做干净包启动和隔离宿主安装；有AI/MCP时分别走真实入口。尽早暴露清单预算、Schema方言、运行依赖和宿主响应结构问题，不等全部功能写完才第一次安装。

详细接入和目录规则见 [开发约定](development.md)；Ctool 的 [模块任务入口](../ctool/doc/tasks/cookieos-migration/README.md) 可参考组织方式，不照搬其业务任务数量和目录层次。

## 完整AI/MCP的复用经验（2026-10-31）

适用：Ctool 0.3.0、SDK1.2.0/hostApi ^1.0.0的Vue/Node实现。依据：[详细设计](../ctool/Detailed-Design.md)、[研究与选型](../ctool/doc/research/full-ai-mcp.md)、[最终检查](../ctool/doc/verification/full-ai-mcp/checks.json)、[隔离宿主结果](../ctool/doc/verification/full-ai-mcp/host-results.json)。下面的办法可复用，具体库版本、预算和工具名称需按新插件核实。

### 先盘点操作，再设计工具

- 页面分类、路由、原子操作、服务工具名和模型辅助数量分别统计。Ctool当前是60类/88入口/100个服务工具，12类页面模型辅助包含13种操作；不是100项新增算法，也不是每个按钮各建一个接口。
- 从实际页面列出算法、输入/输出、选项和失败行为，映射到模块与可执行用例。Ctool的[覆盖矩阵](../ctool/doc/tasks/full-ai-mcp/capability-matrix.md)、[用例夹具](../ctool/tests/fixtures/capability-cases.json)可参考组织方式。名称齐全只能证明注册覆盖，不能证明全部选项可用或所有组合都测过。
- 有旧接口时先冻结名称、参数、结果和effect，再逐字段回归。扩展能力优先新增工具或operation，不悄悄扩大旧枚举、改结果类型或迁移存储键。工具声明、服务校验和最终manifest使用同一个注册来源。
- 共用纯业务规则；浏览器密钥、DOM、宿主桥和管理服务器网络在各自边界适配。共享代码不反向导入Vue/store，也不让另一个插件直接依赖Ctool内部文件。浏览器原本本地处理的密钥不因共用算法而自动上传。

### 这轮实际踩过的坑

| 已复现问题 | 可复用处理 | 复核条件 |
|---|---|---|
| SDK check通过，真实安装仍提示清单过大；同一manifest缩进版288800字节、紧凑版125198字节 | 对最终序列化UTF-8字节做预算断言，允许压缩排版，保留全部工具和校验；这组数字来自修复时的候选，最终包见artifact收据 | 工具、Schema或宿主预算变化；不把字符数当字节数 |
| 插件、宿主调度、MCP和模型返回不同的成功标志 | 分别核对插件callId/ok/result、宿主state/result、MCP isError/structuredContent与模型status/execution，沿实际SDK/宿主响应处理 | 宿主协议或客户端变化 |
| CJS包动态import后的命名空间与预想不同，运行时报parse不是函数 | 使用已验证的公开共享入口，检查最终bundle的真实导出；类型检查不能替代打包后调用 | ESM/CJS、动态导入或分包变化 |
| 第三方缓存用普通对象，遇到__proto__键产生无效JSON；Properties树还可能污染原型 | 用自有键判断/null-prototype字典保留键为数据；第三方缺陷使用锁定的正式包补丁，不手改node_modules，留下同进程及后续调用回归 | 解析/序列化库或补丁变化 |
| Ajv异步Schema返回Promise，被同步代码当成valid=true | 明确工具是否支持异步；同步接口在编译前拒绝$async，测试先证明错误再修复，不复制校验器 | 校验模式或返回类型变化 |
| 大文件SM3使工作进程退出 | 复用Node原生摘要/HMAC，保留共享盐值表达式，与浏览器provider做已知向量交叉验证；小文本正确不代表大文件资源可承受 | provider、编码或规模变化 |
| 签名库新版本删除原RSA加解密API | 按实际版本拆分签名与加解密，优先标准API，缺口用成熟库；做浏览器/Node交叉往返，不只验一端自加自解 | 库、密钥格式、填充或平台变化 |
| 二维码Byte模式中文截断；部分圆点+Logo无法回读 | 显式处理UTF-8字节，用独立解码器回读输出；不可识别时明确失败，不偷偷修改样式 | 库/fork、编码、样式或Logo变化 |
| 构建清理与依赖复制并发，留下半个运行目录 | 构建、准备运行依赖、组装、验包串行，产物有唯一写入顺序 | 构建脚本或并行CI变化 |
| 多份服务测试并行压CPU，条码触及截止，独立复跑正常 | 先复现测量；独立实例压力用例按文件串行，同实例并发/队列/超时仍单独测试，不提高产品截止掩盖干扰 | 测试并行度、资源或原生依赖变化 |
| 打包前审计发现Sharp传递依赖高危漏洞 | 查官方公告与实际运行闭包，升级到已核实修复版，同时更新开发锁和部署锁，重做图像/干净包/最终ZIP验收 | 本次修复版0.35.5不是未来固定推荐；audit为0也不等于没有漏洞 |

### 文件、长任务和外部动作

- **预算看完整链路。** 先核对宿主请求/结果上限，再设计上传、计算和下载。Base64约膨胀为4/3，Hex为2倍；分别限制原始块、业务输入、生成输出、总额及对象数。Ctool采用48KiB块、8MiB输入、16MiB输出，不要求新插件照抄。
- **文件结果必须取得到内容。** 用随机临时引用、size/SHA256、commit、分块读取、到期/关闭清理；同偏移同字节确认重传，冲突拒绝。不接受浏览器本机路径，也不把服务器路径当文件结果。私钥等敏感输出用短期文件引用并准确标注effect。
- **引用不等于用户授权。** 当前工具协议不携带最终用户身份，随机能力引用不能宣传为逐用户ACL。需要互不信任用户隔离时先核定宿主身份合同，不在插件中猜用户ID。
- **取消必须停止实际工作。** 同步正则、表达式或密码计算不能靠Promise.race终止。Ctool使用固定可信子进程、有限并发/队列和真实终止；不能扩为任意系统命令。排队也计入截止，验证取消后健康、容量恢复和子进程清理。
- **限制各有边界。** JS堆限制不是原生库/ArrayBuffer/RSS硬上限，像素预算不是内存上界。Ctool实际采样8MiB文件场景进程树峰值约510MiB，不是所有图片或新插件的内存保证。
- **模型复用SDK生命周期。** 创建/运行、事件、status和cancel使用同一调用身份；并发预算包含尚在创建的请求。断流查原调用，保留部分文本和unknown状态，不自动重发可能计费的生成。
- **网络发送不冒充对端业务成功。** WebSocket用稳定messageId、内容摘要及有界状态记录；同ID同内容不重发，内容变化拒绝。接收cursor确认旧消息并重读保留部分；溢出、丢失、过期和关闭要可见。认证从秘密配置引用，拒绝内嵌凭据URL及可能泄漏认证的重定向。

## 接入时最容易遗漏的边界

适用：本次核实的 SDK 1.1/1.2 UI/Node 接入。依据：[Ctool 设计](../ctool/High-Level-Design.md)、[服务合同测试](../ctool/tests/contract.test.mjs)、[浏览器测试](../ctool/tests/browser/plugin.spec.ts)。SDK、模型协议、宿主授权方式或服务生命周期变化时重新核对。

- UI 挂载使用模板入口及 `#app`，通过 `window.xhub` 访问宿主。`requires` 是桥能力，`permissions` 是权限；打开外链按实际合同声明 `open-url`。不能导入宿主私有前端模块。
- 插件服务运行在 cookieOS 管理服务器；浏览器中的 IP 查询、WebSocket 和文件操作可能发生在访问者电脑。逐项说明执行位置，不能把服务器操作描述成本机操作。
- 复用模板的随机端口、就绪消息、实例身份、健康接口和服务令牌校验。工具调用同时核对 HTTP 状态、业务 `ok` 和对应调用 ID；参数、结果都有边界校验。
- 配置先分普通偏好和秘密；秘密由宿主注入，不放进前端、manifest、日志或 ZIP。原工具已有供应商密钥设置时，接宿主模型后检查是否应移除旧入口，避免维护两套配置。
- 模型目录可读取不等于模型能完成生成。发起、取消、超时、切页、输入变化和断流分别处理；未知结果保留调用身份并查询原状态，不能自动重新发起生成或外部写操作。
- 高耗时解析、正则、压缩、二维码及执行引擎要有适当输入限制和可终止边界。Ctool 的具体时限和大小是其业务选择，不是后续插件的统一默认值。
- 原 HTML 壳可能有弹层节点、初始化顺序等隐含依赖。迁移到宿主入口时同时检查页面、弹层和 Worker 资源，不能只替换入口文件。

## SDK 1.2 展示资料：一份身份，两类文件

适用：SDK 1.2.0 的 presentation-metadata 合同。依据：[实际 manifest](../ctool/manifest.json)、[实际 metadata](../ctool/metadata.json)、[SDK schema 快照](../ctool/contracts/metadata.schema.json)、[组装入口](../ctool/scripts/assemble.mjs)。升级 SDK、宿主展示格式或资源预算时复核；快照用于追溯，不替代新插件取得的 SDK。

| 文件或版本 | 维护内容 | 容易混淆的地方 |
|---|---|---|
| SDK `sdkVersion` | 开发包版本，本次为1.2.0 | 不把运行清单的 schemaVersion 改成1.2 |
| `manifest.json`，schemaVersion=1 | ID、名称、作者、插件版本、简介、分类及运行能力 | 不把图标/截图等展示字段塞进严格运行清单；也不把 hostApi 当宿主软件版本 |
| `metadata.json`，schemaVersion=1 | 包内图标、介绍、截图、纯文本更新、真实HTTPS链接及许可证 | 不重复身份/版本/能力，不自行填写官方认证、安装量、评分或兼容结论 |
| SDK 导出的 `item.json` | 最终ZIP的身份、摘要、大小、运行要求及展示投影 | 是构建产物，不是第二份手工维护的 manifest；不能复用临时地址发布 |

- **运行身份只维护一次。** Ctool 由源 manifest 提供身份和版本，Vite 从它注入界面版本，现有业务定义生成 tools 后写入最终 manifest。复用这种单一来源原则，不要求每个插件都使用 Vite，也不要复制其全部构建脚本。
- **开发说明与用户介绍分开。** Ctool 将 `presentation/README.md` 复制成包根 `README.md`；根开发 README 保留构建/验收说明。用户介绍只写已实现用途、步骤、必要配置、费用/数据影响和限制，不依赖脚本、iframe、远程图片或内联样式。图片通过 metadata 的 screenshots 声明。
- **使用真实素材。** 优先复用有许可依据的品牌图标；截图取自实际运行页面，使用脱敏示例输入。预览桥或模拟模型要写明，不能把模拟生成结果当成真实模型能力。Ctool 的主许可证和依赖许可证分别保留，不能把主许可证当成所有复用代码的许可证。
- **截图先清场再捕获。** 关闭无关搜索下拉、提示和弹层，等待实际操作、图片加载与过渡结束，再检查成图。此次资料弹窗早期截图捕获了透明过渡，等待稳定并使用截图的 `animations: 'disabled'` 后复核；不能用动画中间帧证明布局。图片应能在详情预览中辨认内容，不只检查文件存在。
- **校验交给 SDK 和宿主。** 使用其字段允许集、路径/字节预算及安装器的图片格式/尺寸校验；插件只补自己的集成断言，不自写另一套图片或路径校验器。本次图标512×512、三张截图1074×500，是实际素材尺寸，不是所有插件必须采用的尺寸。
- **数量从实现取。** UI 工具数、功能入口数、UI 模型辅助数、后台工具数、AI/MCP 开放数分别统计。0.2.0盘点是60/88/12/17/14，见[历史盘点](../ctool/docs/sdk-1.2-inventory.json)；0.3.0服务工具及AI/MCP均为100，见[当前收据](../ctool/doc/verification/full-ai-mcp/checks.json)。新插件重新枚举，不复制这些数字。难以稳定统计就不用数量作宣传。

## 验证与打包时的经验

适用：本次 Ctool 的 Vue/Node 构建和 SDK 1.1/1.2 打包流程。依据：[构建任务](../ctool/doc/tasks/cookieos-migration/09-build-package.md)、[包测试](../ctool/tests/package.test.mjs)、[交付记录](../ctool/docs/delivery.json)。构建器、依赖或安装器变化时复核。

- 验证分开记：业务单测、服务合同、页面交互、隔离包启动、SDK 预检、真实宿主验收各自证明不同事项。0.1.0的343个业务单测、0.2.0的22项服务合同/7项包测试/22项浏览器用例分别有记录，不写成每次发布都重跑了所有检查。
- 用真实控件和结果断言页面可用；对话框要实际打开，二维码/加解密等按行为验证往返。测试定位或断言错误先修测试，不直接归因为产品缺陷。
- 默认执行项目已有验证入口；小改动先跑受影响检查，SDK/依赖/公共行为变化再扩大。新增重复检查应拒绝真实反例，不重建基线或提高阈值掩盖新增重复。
- SDK `check` 只做本地文件预检。另查 schema、相对资源路径、Worker/WASM、服务入口和运行依赖；Node 包在没有开发 `node_modules` 的新目录启动，不能因开发目录可跑就判定可部署。
- 先组装安装专用目录，再 `check` 和 `pack`。ZIP 根目录直接包含 manifest 和入口；排除开发框架、源码规划文档、凭据、运行数据和无关平台产物，ZIP 本身放在插件目录之外。
- 源码、预览构建和已生成 ZIP 是三个对象。改了源码并刷新预览，不会更新旧 ZIP。构建来源、最终ZIP摘要和验收绑定；已通过验收且没有变化的ZIP直接发布，不为发布再构建一次。包内内容变化才重新构建、打包、生成条目并复验。旧文件保留，新输出选未占用路径；公网版本一旦发布就不覆盖资产，后续修复递增版本。
- 构建实际包含的依赖与整个工作区依赖分开审计。许可清单要覆盖 UI、全部 Worker 和服务，保留相关许可证及所需源码材料；有构建告警和未验项就按范围记录，不能宣称绝对无漏洞、无 bug。

## 市场发布这次验证了什么

适用：本仓库当前市场合同、SDK 1.2.0 和 Ctool 0.2.0 GitHub预发布。依据：[市场维护](market.md)、[公开下载与验签收据](../ctool/doc/verification/sdk-1.2/github-release.json)、[发布记录](../ctool/Progress.md)。目标宿主、GitHub 下载策略或市场协议变化时复核。

**推送源码不会自动让市场发现插件。** 本次经过验证的发布顺序是：

1. **固定已验收产物。** 先有最终ZIP、来源提交、摘要和隔离安装证据。没有发布授权时停在本地交付，保留未生成的正式条目，不虚构地址或时间。
2. **等待源码推送真正完成。** 确认远端已有目标提交，再创建版本专属Release草稿。异步工具返回session并不表示push成功；本次过早创建曾得到 `target_commitish is invalid`，待push完成后重试成功。不要因此换到错误提交或绕过版本核对。
3. **上传原ZIP、摘要和摘要命名的媒体。** 草稿阶段可复用此前从同一ZIP导出的媒体字节，逐项核对状态、数量和大小；不上传临时item。GitHub自动生成的Source code ZIP不能当插件包。
4. **公开后读取真实发布时间。** 使用GitHub实际 `publishedAt`，再用SDK `market-item` 从同一个ZIP和真实URL生成正式item及媒体。输出文件和目录必须不存在；隔离导出与正式导出分目录保存。本次媒体先已公开，正式导出后重新核对每个文件相同，未覆盖发布资产。
5. **媒体URL匹配实际托管方式。** GitHub Release资产是平铺文件，asset-base-url用版本的 `/releases/download/<tag>`，SDK追加内容摘要文件名；不要凭示例多拼一个不存在的 `/assets`。下载ZIP也用固定tag，不用latest地址。
6. **匿名验证全部公开产物。** HTTPS正常验书，检查ZIP、摘要文件、图标和每张截图的状态、大小及内容摘要；正式item上传后逐字节核对SDK输出。认证管理API能读资产不等于公众能下载。
7. **只合入SDK生成的条目。** 不手写摘要、包大小、要求投影或媒体映射；更新目标ID、保留其他插件、确保ID唯一。增加仓库级sequence和有效期，用原密钥签原始字节，正常验签及篡改反例通过后，同次提交清单与签名。私钥保持本地，不随源码或资产上传。
8. **推送后复核公开清单。** 重新下载实际main清单、签名和公钥，确认条目与正式item一致，序号正确且验签通过。资料字节未变时不无理由重建或重跑全套业务测试。

0.2.0已在独立宿主通过真实HTTPS测试市场的刷新和精确版本安装，随后验证GitHub公开资产及sequence 3清单；**未操作正式cookieOS实例重新安装**。测试市场安装、公开资产可读和正式实例安装分别记录，不能合并成一个“上线全部通过”。预发布也不代表所有兼容性和外部模型已验收。

新版宿主支持填写 GitHub 仓库首页或 HTTPS 清单地址；旧版固定公钥模式还需配置公钥。本仓库继续提供签名以兼容旧模式，具体配置按 [市场维护](market.md) 执行。新增插件时追加其条目、保留其他插件并保证 ID 唯一；发布包和版本独立，市场序号属于整个仓库。

## 下一次交付前的简短复核

- 文件：源码目录、模块任务、实际入口、构建输出和插件外部 ZIP 均真实存在，文档链接有效。
- 合同：SDK与两类schema版本区分，工具Schema方言可由宿主编译；桥能力、权限、模型/工具入口、执行位置及配置来源与实现一致。
- 展示：身份只在manifest维护；metadata资源存在、有许可、内容准确、限制满足；真实截图稳定且脱敏，缺字段和坏图有适用检查。
- 产物：包包含全部运行依赖、资源和许可，不含秘密、运行数据、本地开发框架；记录版本、来源提交、SHA256和实际检查。正式item对应最终ZIP及真实地址/时间，不含临时服务地址。
- 发布：已有授权才推送或发布；要求只保存到本地时不自动上传。源码推送、Release 公开、市场登记、真实安装分别记录。
- 验收：正常路径、失败、超时、结果未知及受影响旧行为有相称检查；未验项明确列出，不能承诺零 bug。
- 收尾：主目录接入了验证过的改动，预览使用正确产物；清理本次 worktree，保留历史发布包与回退依据。
